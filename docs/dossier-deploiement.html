3 · Les tokens Turso : d'où ils viennent

La base ne vit pas dans le projet : elle est hébergée chez Turso. Le code a besoin de deux informations pour s'y connecter, toutes deux stockées dans des variables d'environnement préfixées VITE_.

VariableCe que c'estOù la trouver chez Turso
VITE_TURSO_DATABASE_URL L'adresse de la base, au format libsql://<nom>-<compte>.aws-eu-west-1.turso.io (69 caractères) Tableau de bord Turso → base gestion-etudiants → Database URL (ou turso db show <nom> --url)
VITE_TURSO_AUTH_TOKEN Un jeton JWT signé (348 caractères, commence par eyJhbG…) qui autorise la lecture et l'écriture Turso → base → Create Token (choisir « Read & Write »), ou turso db tokens create <nom>
Règle : le jeton est affiché une seule fois à sa création. S'il est perdu, on en crée un nouveau et on révoque l'ancien (turso db tokens revoke). C'est aussi le geste à faire si un jeton a pu fuiter.

Le schéma de la base

CREATE TABLE IF NOT EXISTS students (
  id        TEXT PRIMARY KEY,
  firstname TEXT NOT NULL,
  lastname  TEXT NOT NULL,
  email     TEXT NOT NULL UNIQUE,
  ...
);

Le schéma (database/schema.sql) est appliqué une seule fois avec bun database/setup.mjs, qui utilise les mêmes identifiants.

Premier emplacement : le fichier .env local (non versionné)

# .env — à la racine du projet, jamais commité
VITE_TURSO_DATABASE_URL=libsql://gestion-etudiants-<compte>.aws-eu-west-1.turso.io
VITE_TURSO_AUTH_TOKEN=eyJhbGciOi...   (348 caractères)

En développement, Vite lit ce fichier au démarrage. Il faut redémarrer bun run dev après toute modification.

4 · Où coller les tokens dans Cloudflare

Sur Cloudflare, le build se fait dans un conteneur vierge : le fichier .env n'existe pas. Il faut donc redonner les deux valeurs à Cloudflare, comme variables de build (et non comme variables d'exécution), parce que Vite les fige dans le JavaScript pendant la compilation.

1 · BuildVite lit les variables et écrit les valeurs dans dist/assets/*.js
→
2 · Deploywrangler envoie dist/ sur le réseau Cloudflare
→
3 · Visiteurle bundle contient déjà l'URL et le jeton

Étape par étape dans le tableau de bord

  1. Cloudflare → Workers & Pages → ouvrir le projet gestion-des-etudiants.
  2. Onglet Settings (accessible aussi via le chevron « S > » de la barre d'onglets).
  3. Section Build : vérifier
    • Build command : bun run build
    • Deploy command : npx wrangler deploy --config wrangler.jsonc
  4. Section Variables and secrets (« No build variables or secrets configured ») → bouton + Add.
  5. Ajouter les deux entrées, une par une, en séparant bien le nom et la valeur :
    NameValueType
    VITE_TURSO_DATABASE_URLl'URL libsql://… complète (69 caractères)Text
    VITE_TURSO_AUTH_TOKENle jeton complet (348 caractères, à partir de eyJhbG)Secret (recommandé)
  6. Save, puis onglet Deployments → Retry deployment (ou un git push). Les variables n'agissent qu'au build suivant : sans redéploiement, rien ne change.

Les erreurs à ne pas commettre

  • Coller VITE_TURSO_AUTH_TOKEN=eyJ… dans la valeur : seul le texte après le « = » compte.
  • Laisser des guillemets "…", un espace ou un retour à la ligne en trop.
  • Copier un jeton tronqué (348 caractères exactement).
  • Utiliser une variable d'exécution (runtime) au lieu d'une variable de build.

Comment reconnaître la cause d'une panne

Message affiché par le siteCause
« Base de données non configurée »Les variables manquent au build, ou le déploiement n'a pas été relancé
« Identifiants de la base invalides » (401)Jeton erroné, tronqué ou révoqué
« La table students est introuvable »Le schéma n'a pas été appliqué sur cette base
Le site fonctionne normalementTout est correct
Preuve technique : la taille du bundle change selon la présence des variables (276,05 kB sans, 276,46 kB avec). La différence de ~0,4 kB correspond au jeton inscrit dans le fichier — c'est la démonstration que les valeurs sont bien figées au build.

5 · Les problèmes rencontrés et leurs solutions

Cinq blocages se sont succédé. Chacun a été isolé, corrigé par un commit dédié, puis validé par un nouveau déploiement.

Problème 1

Le fichier _redirects arrivait corrompu (CRLF)

Symptôme
La règle « /* /index.html 200 » était vue comme invalide ; les fins de ligne Windows (\r\n) s'ajoutaient au fichier, que le serveur ne savait plus lire.
Cause
Git pour Windows convertit les fins de ligne ; le fichier était interprété comme contenant un caractère parasite.
Solution
Un fichier .gitattributes force le format Unix pour ce seul fichier : 
* text=auto
public/_redirects text eol=lf
Vérification
od -c dist/_redirects : plus aucun \r (contrôlé en local, dans un clone et dans le build). Commit dfc1d45.
Problème 2

Cloudflare refusait le projet : « Vite ≥ 6 requis »

Symptôme
✘ The version of Vite used in the project ("5.4.21") cannot be automatically configured. Please update the Vite version to at least "6.0.0" — le build passait, le déploiement échouait.
Cause
L'auto-configuration de Cloudflare Workers Builds analyse le projet et impose Vite 6 ; elle ignorait notre fichier wrangler.jsonc (le journal affichait gestion-des-etudiants au lieu du nom prévu).
Solution
Court-circuiter l'auto-configuration en imposant le fichier de configuration dans la commande de déploiement : 
# Settings → Build → Deploy command
npx wrangler deploy --config wrangler.jsonc
Aucune montée de version de Vite n'a été nécessaire.
Problème 3

Le nom du Worker ne correspondait pas au projet

Symptôme
▲ [WARNING] Failed to match Worker name. Your config file is using the Worker name "gestion-etudiants", but the CI system expected "gestion-des-etudiants".
Cause
Le nom écrit dans wrangler.jsonc différait de celui du projet Cloudflare, qui imposait le sien.
Solution
Aligner la configuration sur le projet : 
"name": "gestion-des-etudiants"
Vérification
Plus aucun avertissement dans les journaux suivants. Commit dc9ca1f.
Problème 4

Erreur 100324 : « Infinite loop detected »

Symptôme
Au moment de créer la version du Worker : 
Invalid _redirects configuration:
Line 1: Infinite loop detected in this rule.
[code: 100324]
Cause
La règle /* /index.html 200 était prévue pour Cloudflare Pages. Sur les assets Workers, le repli SPA est déjà assuré par not_found_handling: single-page-application : les deux mécanismes se cumulaient et formaient une boucle.
Solution
git rm public/_redirects — le routage est désormais entièrement décrit dans wrangler.jsonc (voir annexe A). Le build est repassé au vert immédiatement.
Problème 5

Le site s'afficherait sans base de données

Symptôme
Après un déploiement réussi, l'application aurait affiché « Base de données non configurée », car le conteneur de build de Cloudflare ne contient pas le fichier .env.
Cause
Vite remplace import.meta.env.VITE_* par des valeurs littérales pendant le build : sans variables, la chaîne est vide et le client n'est pas créé.
Solution
Ajouter les deux variables dans Settings → Build → Variables and secrets (section 4), puis relancer le déploiement. Contrôle : la taille du bundle passe de 276,05 kB à 276,46 kB, preuve que les valeurs sont intégrées.

6 · Vérifications après déploiement

  • La page d'accueil s'affiche (pas d'écran blanc, pas de 404).
  • Connexion avec le compte de démonstration : admin@ecole.ma / admin123.
  • La liste /etudiants affiche les données de la base Turso.
  • Rafraîchir (F5) sur /etudiants ne casse pas la page — c'est le rôle du repli SPA.
  • Créer un étudiant, recharger, vérifier qu'il est toujours là (preuve que l'écriture fonctionne).
  • Modifier puis supprimer cet étudiant de test.
  • Le cadenas HTTPS est présent sur l'URL *.workers.dev.
Résultat obtenu : 105 modules transformés, bundle de 276 kB (84,6 kB compressé), build en 1,4 s, déploiement en une vingtaine de secondes — pour un coût d'hébergement de 0 € par mois.

Le point à traiter ensuite : le token dans le bundle

Puisque le token est figé dans le JavaScript public, n'importe qui peut lire et modifier la base. La correction tient en un petit Worker intermédiaire :

Avantnavigateur → Turso, avec le token visible
→
Aprèsnavigateur → Worker /api → Turso, token stocké en secret côté serveur

Le Worker valide la session, n'expose que les requêtes prévues, et le secret est saisi dans Settings → Variables and secrets sans jamais apparaître dans le code. À faire avant toute utilisation réelle.

Nom de domaine

Le sous-domaine *.workers.dev est gratuit. Un domaine personnel (ex. .com) s'achète à part — environ 11 $/an chez Cloudflare Registrar — puis se rattache dans Settings → Domains & Routes → Add → Custom domain ; le certificat HTTPS est généré automatiquement.
